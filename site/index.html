01

Both sides stay current

Start rung watch and leave it running. When you save a file, rung imports it through Openness, compiles the block and writes TIA's version back, so the file always matches the project. Change something in TIA Portal and the file follows within a couple of seconds. If both sides changed, rung merges: SCL line by line, LAD and FBD network by network, so two people working on different networks of one block both keep their change. A real conflict stops and shows you both sides, and a sync cut off halfway picks up where it stopped.

02

An editor that knows SCL

The language server completes variables and members, jumps to definitions through DBs, UDTs and FB instances, finds references and renames safely. Compile errors from TIA Portal land on the line they belong to, and the values of a running block appear at the end of its lines, like TIA's monitoring. There are extensions for VS Code and Zed, and a short config for Neovim. TwinCAT and CODESYS structured text work too.

03

Tests for blocks, without a PLC

Describe a few scan cycles in YAML and rung test runs them on an offline simulator: SCL, LAD, FBD, STL and structured text, with virtual time, IEC timers and counters, edges and common system instructions. What it does not model, a test replaces with a stub, and anything else it refuses by name instead of guessing. No PLC, PLCSIM or TIA Portal, so it runs on any CI runner, Linux too, and a failed step shows on its line in the pull request. 

# tests/motor.test.yaml
block: Fx_Motor
cases:
  - name: starts and latches
    steps:
      - set: { Start: true, SpeedSetpoint: 1500 }
      - cycle: 1
      - expect: { Running: true, SpeedOut: 1500 }

$ rung test
ok   Fx_Motor: starts and latches
1/1 passed (offline simulation — not a PLCSIM run)
04

Agents edit files, not the project

Claude Code, Codex and Cursor change the text files like any other code, and rung carries the change into TIA Portal. A small MCP server gives them what the files can't: sync status, compile results, cross references and the test runner. rung setup connects every agent it finds, with skills for the sync workflow, for keeping away from safety code, and for reviewing a change before it goes in. Downloads to a PLC stay with a person.

05

A review that knows PLCs

rung Pro reads a change the way a controls engineer does: the interface variable by variable, attributes such as optimized access and retain, the logic per region and per LAD or FBD network, tag addresses, network settings, and which callers and instance DBs it touches. Nothing it cannot explain is ever called formatting. It gates pull requests in your own CI and writes the change record for FAT and SAT. 

$ rung-pro review --fat --out FAT-v1.5.md
## plc/PLC_1/blocks/Fx_Motor.scl (modified)
FB Fx_Motor — modified
| + | Output | Ready | | Bool |
Logic:
- #Overspeed := #Speed > 3000.0;
+ #Overspeed := #Speed > 2500.0;
+ #Ready := #Running AND NOT #Overspeed;
Affected (callers, instances, users): Main
## Sign-off  author · reviewer · safety · customer

Careful by default

  • It talks to TIA Portal only through Siemens' Openness API and never opens project files itself.
  • It never downloads by itself. A person starts every download, types the PLC name and allows each risky question TIA asks by name. Live values come from the S7-1500 Web API, read only.
  • Failsafe, know-how protected, system and GRAPH blocks and instances of library types are exported for reading and never imported.
  • Imports run inside a TIA transaction and check the block's revision first. If someone changed it in the meantime, rung merges or stops.
  • Deleting a file never deletes a block. You confirm that yourself with rung confirm-delete.
